## 3. 계획에서 구현까지

### 3.1 서비스 범위 재정의

초기 기획에는 농작물·축산 피해가 함께 포함되어 있었다. MVP의 완성도를 높이기 위해 Codex에 기존 코드와 화면의 농작물, 작목, 경작면적 중심 표현을 찾아 축종, 사육두수, 축사, 폐사·부상 가축, 축산시설 피해 중심으로 바꾸도록 요청했다.

AI가 공식 피해율, 손해액, 지원 자격이나 지원금 지급 여부를 확정하지 않도록 결과를 신고·신청 준비용 보조 정보로 제한했다.

### 3.2 고령 사용자 중심 UI

모바일 화면 너비와 하단 내비게이션을 통일하고 다음 원칙을 반복 적용했다.

- 큰 글자와 충분한 명도 대비
- 한 화면에 하나의 주요 행동
- 사진과 음성을 우선하는 짧은 입력 흐름
- 아이콘만 쓰지 않고 이해하기 쉬운 텍스트 병기
- AI 질문과 사용자 발화를 채팅 형태로 동시에 표시
- 녹음 상태, 다시 말하기, 직접 고치기 기능을 명시적으로 제공

초기 화면의 분위기는 초록색을 주색으로 정리하고 소 캐릭터를 서비스 로고와 AI 대화 프로필로 활용했다. 전체 컴포넌트의 위치를 무리하게 바꾸지 않고 공통 색상, 카드, 타이포그래피, 버튼과 하단 바를 중심으로 디자인을 통일했다.

### 3.3 핵심 사용자 흐름

구현한 데모 흐름은 다음과 같다.

```text
로그인/회원가입
→ 축산농가 온보딩
→ 홈
→ 촬영 전 안전 안내
→ 피해 사진 등록
→ 음성 피해 설명
→ 누락정보 추가 질문
→ 피해 내용 요약
→ 증빙자료 준비
→ 문서 초안 및 PDF 저장
```

### 3.4 OpenAI API 연결 구조

브라우저의 `MediaRecorder`로 사용자의 음성을 녹음하고 서버 API에서 처리하도록 구성했다.

```text
마이크 녹음
→ POST /api/voice/transcribe
→ 음성 텍스트 변환
→ POST /api/voice/chat
→ 피해정보 구조화 및 다음 질문 생성
→ 채팅 UI와 요약 화면 반영
```

구조화 필드는 발생 시점·위치·재해 유형·축종·평상시 사육두수·폐사 및 부상 수·시설 피해·피해 설명·복구 필요사항을 중심으로 설계했다. 이미 확인된 내용을 다시 묻지 않고, 지원 탐색과 신고 준비에 필요한 누락정보만 한 번에 하나씩 질문하도록 프롬프트와 응답 스키마를 조정했다.

## 4. 반복 수정과 오류 복구

### 4.1 Windows에서 개발 명령이 실행되지 않음

초기 `npm run dev` 스크립트는 다음과 같은 Unix 스타일 환경변수 선언을 포함하고 있었다.

```text
WRANGLER_LOG_PATH=.wrangler/wrangler.log vinext dev
```

PowerShell에서는 `WRANGLER_LOG_PATH`를 실행 명령으로 인식해 실패했다. Codex가 실행 환경과 패키지 스크립트를 확인한 뒤 Windows에서도 바로 동작하는 `npx vinext dev`와 `npx vinext build`를 사용해 개발·검증 절차를 정리했다.

### 4.2 패키지 매니저 혼용

저장소에 npm과 pnpm 관련 파일이 함께 있었고, 로컬 환경에는 pnpm이 바로 준비되어 있지 않았다. Corepack을 통한 실행 과정에서도 네트워크 및 빌드 스크립트 문제가 발생했다. 최종적으로 현재 환경에서 안정적으로 설치 가능한 npm 기준으로 의존성을 정리하고 빌드를 재검증했다.

### 4.3 `.env.local`이 존재하지만 API가 동작하지 않음

파일 이름은 맞았지만 실제 크기가 0바이트여서 키가 저장되지 않은 상태였다. 보안을 위해 Codex는 키 문자열을 출력하지 않고 파일 존재 여부와 크기만 확인하도록 안내했다. 저장 후 로컬 API 요청으로 정상 연결 여부를 검증했다.

### 4.4 로컬에서는 되지만 배포 환경에서 환경변수를 읽지 못함

Cloudflare Workers 환경에서는 일반적인 `process.env` 접근만으로 Secret을 읽지 못하는 문제가 있었다. 런타임에 맞게 `cloudflare:workers`의 환경 바인딩을 사용하도록 수정하고, 배포 서비스에는 `OPENAI_API_KEY`를 Secret으로 등록했다. 키는 저장소나 로그에 포함하지 않았다.

### 4.5 고정 설문처럼 반복 질문함

첫 버전은 질문 목록을 순서대로 소진하는 방식에 가까워 사용자가 이미 말한 내용도 다시 물을 수 있었다. Codex에 인터뷰 목표를 다시 명확히 전달해, 매 응답마다 전체 누적 정보를 구조화하고 비어 있는 필수 항목 중 가장 중요한 하나만 질문하도록 변경했다.

다음 문장으로 실제 API 흐름을 확인했다.

> 어제 폭우 때문에 축사가 침수됐고 한우 40마리 중 두 마리가 죽었어요.

첫 응답에서 발생일 `2026-08-15`, 폭우, 한우, 평상시 40마리, 폐사 2마리와 축사 침수를 추출했고, 이미 말한 정보를 반복하지 않고 부상 가축 수만 추가 질문했다. 사용자가 “다친 소는 없어요”라고 답한 뒤 완료 요약으로 진행되는 것을 확인했다.

### 4.6 증빙·문서 준비 버튼에서 런타임 오류 발생

팀원 코드 병합 후 홈과 음성 대화는 동작했지만 `증빙과 문서 준비하기` 버튼을 누르면 `EvidenceChecklist is not defined` 오류가 발생했다. 호출부는 남아 있었으나 컴포넌트 정의가 병합 과정에서 빠진 것이 원인이었다. 기존 디자인 클래스와 데이터 흐름을 보존하면서 컴포넌트를 복구해 화면 이동이 끊기지 않도록 수정했다.

### 4.7 팀원 기능과 디자인 변경의 충돌

원격 main에는 팀원이 추가한 폭설 사례, 신고 준비 기능과 PDF 기능이 있었고 로컬에는 모바일 디자인, 음성 UI와 API 연결 변경이 있었다. 원격을 먼저 확인한 다음 기능은 팀원 구현을 우선 보존하고, 색상·타이포그래피·아이콘·모바일 레이아웃은 로컬 디자인을 기준으로 수동 병합했다. 생성 파일은 커밋에서 제외하고 실제 소스와 자산만 반영했다.

### 4.8 첫 배포 시 일시적인 TLS 오류

첫 공개 배포에서 인증서 연결이 시간 초과되어 실패했다. 코드 오류와 외부 연결 문제를 구분하기 위해 로컬 프로덕션 빌드를 다시 확인하고 같은 빌드 버전으로 배포를 재시도했다. 두 번째 시도에서 배포가 정상 완료되었고 공개 URL 접속과 API Secret 등록 상태를 확인했다.

### 효과적이었던 점

- 긴 기획을 화면·데이터·프롬프트·API 작업 단위로 나누어 빠르게 MVP로 전환할 수 있었다.

### 시행착오와 주의점

- Codex가 제안한 명령도 Windows와 Unix 환경 차이 때문에 그대로 실행되지 않을 수 있어 실제 셸 검증이 필요했다.
- `.env.local`은 파일을 만드는 것만으로 충분하지 않고 저장 여부와 배포 환경 Secret을 별도로 확인해야 했다.
- UI 컴포넌트를 병합할 때 화면 모양만 확인하면 호출부와 정의가 어긋난 런타임 오류를 놓칠 수 있었다.
- AI가 구조화한 정보는 공식 행정 판정과 분리해야 하므로 UI 고지와 스키마 제한이 필요했다.
- 배포 실패가 항상 코드 문제는 아니므로 빌드, 환경변수, 호스팅 연결을 나누어 진단해야 했다.
