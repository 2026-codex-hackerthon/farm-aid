# Codex Build Log — 축산 피해 기록·신고 준비 화면

## 1. 담당 작업

- 축산 피해 기록 및 신고 준비 화면의 흐름 점검·개선
- 폭설 피해 사례 모의 데이터와 사례별 사진 연결
- 선택한 피해 사례를 바탕으로 한 신고서 미리보기 및 PDF 저장 기능 구현
- 피해 기록 카드의 가독성 개선과 화면 이동 연결 점검

## 2. Codex에 요청한 내용

- “피해 사례도 3개로 늘려봐”
- “사진 하나마다 각각 다른 사례로”
- “신고 준비에서도 피해 기록처럼 카드가 뜨게 하고, 그 중에 선택해서 신고하는 방식으로”
- “PDF 생성 전에 초안을 화면에 보여주고 해당 내용을 수정할 수 있도록”
- “피해기록 페이지 디자인이 이상한데 이 사례들 세로로 나열할 수 있어?”

## 3. 계획 및 구현 과정

1. 현재 `app/page.tsx`와 `app/globals.css`를 확인해 홈, 피해 기록, 신고 준비 화면이 서로 다른 피해 데이터를 사용하고 있음을 파악했다.
2. 폭설 피해를 중심으로 사용할 공통 `mockDamageCases` 데이터를 만들었다.
   - 축사 지붕 적설
   - 축사 외벽 파손
   - 임시 축사 붕괴
3. 각 사례에 발생일시, 장소, 피해 원인, 가축 피해, 시설 피해, 복구 내용, 지원 경로, 사진을 연결했다.
4. 홈 화면의 진행 중인 피해 기록, 피해 기록 목록, 신고 준비 화면이 같은 선택 사례를 참조하도록 연결했다.
5. 신고 준비 화면에 사례 선택 카드와 신고서 형태의 미리보기를 추가했다.
6. `내용 수정` 버튼을 누르면 발생일시·장소·피해 원인·가축 피해·시설 피해·복구 내용·지원 경로를 수정할 수 있게 구현했다.
7. 수정된 내용을 2쪽 표 형식의 PDF로 저장하도록 `jspdf` 기반 생성 로직을 연결했다.
8. 피해 기록 화면은 사진별 사례를 한눈에 읽을 수 있도록 가로 3열 카드에서 세로 목록 카드로 변경했다.

## 4. 시행착오 및 수정 과정

### 피해 데이터와 화면 흐름 중복

- 문제: Pull 이후 집중호우 기반의 이전 화면과 폭설 기반의 새 화면이 함께 남아, 홈·피해 기록·신고 준비에서 서로 다른 사례가 보였다.
- 원인: 피해 사례 정보가 여러 컴포넌트에 하드코딩되어 있었고, 같은 역할의 화면 코드가 중복되어 있었다.
- 수정: 기존 컴포넌트를 한꺼번에 삭제하지 않고, `mockDamageCases`를 새 공통 데이터 원본으로 두고 새 화면 흐름이 이를 사용하도록 연결했다. 이를 통해 병합 충돌 위험을 줄였다.

### 사진이 한 사례에 몰리는 문제

- 문제: 여러 피해 사진이 하나의 사례에 함께 표시되어 사진과 피해 내용의 대응 관계가 불분명했다.
- 수정: 폭설 사진을 사례별로 한 장씩 배정하고, 각 카드에 해당 사진·피해 원인·피해 현황을 함께 표시했다.

### 피해 기록 화면의 가독성

- 문제: 데스크톱에서 카드가 3열로 배치되어 중장년 사용자가 사진과 피해 내용을 읽기 어려웠다.
- 수정: 한 줄에 한 사례가 보이는 세로 목록으로 변경했다. 데스크톱에서는 사진 왼쪽·내용 오른쪽, 좁은 화면에서는 사진 위·내용 아래로 표시되도록 반응형 스타일을 적용했다.

### PDF 문서 내용의 축약 및 수정 불가

- 문제: PDF 저장 전 내용을 충분히 확인하거나 수정하기 어려웠고, 문서가 너무 간략했다.
- 수정: 신고 준비 화면에 표 형식의 문서 미리보기를 만들고 편집 상태를 추가했다. PDF에는 농장 정보, 재난 정보, 피해 내용, 복구 사항, 지원 경로, 첨부 사진, 신고인 확인 항목을 포함하도록 구성했다.

### 로컬 실행 환경 문제

- 문제: 초기 `npm ci`는 `package-lock.json`과 `package.json` 불일치로 중단됐고, Windows 환경에서 기본 실행 명령도 바로 동작하지 않는 상황이 있었다.
- 수정: 프로젝트의 로컬 실행 도구로 빌드와 서버 기동을 진행하고, 매 변경 후 빌드 성공 여부를 확인했다.

## 7. 결과

- 폭설 피해 사례 3건이 사진과 함께 각각 독립적인 카드로 표시된다.
- 사용자는 피해 사례를 선택한 후 신고 준비 화면에서 동일한 사례를 확인할 수 있다.
- 신고서에 들어갈 주요 내용을 화면에서 수정하고 PDF로 저장할 수 있다.
- 피해 기록 화면을 세로형 카드 구조로 개선해 사진과 텍스트의 가독성을 높였다.
- 빌드와 주요 화면 이동·편집 흐름을 로컬 환경에서 확인했다.

## 8. 보완 필요 사항

- 현재 피해·지원 정보는 데모용 모의 데이터이므로 실제 행정 공고나 백엔드 데이터와 연결이 필요하다.
- PDF의 기관 확인 항목과 일부 복구 안내 문구는 공통 모의 문구이므로, 실제 제출용에서는 선택 사례와 지역 조건에 맞춰 동적으로 구성해야 한다.
- 사용자 입력 및 피해 기록을 새로고침 후에도 유지하려면 데이터베이스 또는 브라우저 저장소 연결이 필요하다.
